# 프론트 디자인 준수 및 서비스 구조 전환 계획서

기준일: 2026-11-17 (Asia/Seoul)  
개정: v3 · 9분류 전환·다른 에이전트 작업 현황·카드 파일명 최종 재확인 반영  
상태: **9분류 계획 확정 / 구현은 현재 10분류 기반으로 일부 진행됨**  
후속 실행 기준: [미완료 작업 감사 및 완성 계획서](REMAINING_WORK_PLAN_2026-11-17.md)

## 1. 목표와 범위

현재 메인 프론트의 디자인을 준수하며 Vue.js·FastAPI·Nginx·Docker Compose 서비스를 완성한다. 제공된 KcELECTRA 기반 **3대분류·9세부감정** 모델을 연결하고, 최대 감정 확률에 따라 서로 다른 3단계 카드 이미지를 제공한다.

이번 개정은 다른 에이전트가 추가한 코드·설정을 읽고 미완료 작업을 정리한 것이다. Vue 화면·API·분석 저장·Compose 기반을 재사용한다. 이 문서를 수정한 사실이 애플리케이션의 9분류 전환 완료를 뜻하지 않는다. 이번 작업은 문서만 변경하며, 모델 실행·빌드·서비스 재시작은 수행하지 않는다.

| 항목 | 개정 결정 |
|---|---|
| 프론트 | 이미 추가된 `frontend/src/` Vue 화면·컴포넌트를 이어서 완성 |
| 디자인 | 기존 메인 스타일·토큰·폰트·레이아웃·인터랙션 준수. 감정 선택지 10→9, 도감 30→27, 제공 카드 콘텐츠는 변경 명세에 명시 |
| 분석 분류 | 긍정 3 + 부정 3 + 중립 3 = 9개. 놀람·당황을 하나의 클래스로 표시 |
| 카드 | 9세부감정 중 최대 확률에 엄격한 초과(`>`)를 적용. 27개 감정·단계 키 |
| 모델 | 제공된 두 FL 체크포인트와 50:50 앙상블 구성 사용. 서비스 기본 후보는 앙상블, 채택은 실제 자원·추론 검증 후 확정 |
| 실행 | 추가된 `backend.app.main:app`, Nginx·Compose 두 서비스 유지·보완 |
| 저장 | 기존 IndexedDB 이름·원문·초안·즐겨찾기·JSON 가져오기 보존. 구형 분석의 호환성은 분류 버전으로 판단 |
| 구조 정리 | 실 서비스 검증 후 구형 진입점·패키지·실험 시안을 정리. 다른 에이전트의 미커밋 작업을 보존 |

계정·서버 기록 저장·기기 동기화·새 데이터베이스·학습 재실행은 범위에 추가하지 않는다.

## 3. 디자인 보존 기준

[BASE-01](../frontend/docs/design/BASELINE_2026-11-17.md)은 전환 전 메인 기준으로 보존한다. 해당 문서의 10감정·30칸 서술은 과거 기준이며 이번 9분류의 목표 수치는 이 계획이 우선한다. Vue가 기존 `scripts/core.js`·`statistics.js` 등을 재사용하므로 “Vue 파일만 고치면 완료”로 판단하지 않는다.

기존 스타일 적용 순서, IBM Plex Sans KR, 테마 10개×밝음/어두움 20조합, 카드 조작·접근성·초점 복귀를 비교한다. 화면 크기는 1366×768, 1440×900, 390×844, 360×640, 320×568이다. 같은 합성 데이터·시각·브라우저·폰트·모션 시점으로 캡처한다.

정당한 차이는 9개 감정명·필터, 27개 도감 슬롯, 새 분석 상태, 제공 카드 콘텐츠다. 그 밖의 화면 차이는 원인과 조치를 남긴다. 과거 캡처를 현재 Vue 검증 결과로 기록하지 않는다.

## 4. 9분류 계약과 카드 판정

목표 taxonomy는 `emotion-cardex-3plus9-v1`이다. 기존 부정 감정 ID 의미를 보존하고 모델 인덱스와 명시적으로 매핑한다.

| 모델 인덱스 | 제공 모델 라벨 | 앱 ID | 대분류 |
|---:|---|---|---|
| 0 | 기쁨·활력 | pos_1 | positive |
| 1 | 만족·감사 | pos_2 | positive |
| 2 | 안정·자신감 | pos_3 | positive |
| 3 | 분노 | neg_3 | negative |
| 4 | 슬픔 | neg_2 | negative |
| 5 | 불안 | neg_1 | negative |
| 6 | 객관적 서술 | neu_1 | neutral |
| 7 | 의문 | neu_2 | neutral |
| 8 | 놀람·당황 | neu_3 | neutral |

새 taxonomy에서 `neu_3`의 의미는 놀람·당황이며 `neu_4`는 사용하지 않는다. 모델 출력 순서를 기존 프론트 배열 위치에 대입하지 않는다. 동률 순서는 앱 ID 기준 `pos_1,pos_2,pos_3,neg_1,neg_2,neg_3,neu_1,neu_2,neu_3`으로 통일한다.

`p=max(9개 전체 확률)`이며, 각 값은 0~1 유한수이고 합계 오차는 `1e-6` 이하다.

| 경계 | 발급 단계 |
|---|---|
| `0 < p ≤ 1/3` | 1 |
| `1/3 < p ≤ 2/3` | 2 |
| `2/3 < p ≤ 1` | 3 |

정확히 1/3은 1단계, 정확히 2/3은 2단계다. 판정 정책 `card-stage-strict-gt-v1`은 유지한다. taxonomy·계약 버전은 갱신한다. 9분류 균등 분포는 `1/9`이며 정상 1단계 카드다. 0만 있는 분포는 무효다. 기존 30·60·90%의 빈 카드 구간을 새 코드에 되살리지 않는다.

## 5. 목표 구성과 데이터 흐름

```text
브라우저 Vue + 기존 IndexedDB
  → Nginx web
      ├─ Vue 빌드·카드 이미지
      └─ /api/ → FastAPI api
                   → 제공된 두 FL 모델
                   → 9감정 softmax 확률 50:50 평균
                   → 9개 앱 ID 매핑·검증
                   → 대표 감정·단계·card_key
```

### 5.1 제공 모델의 실제 의미

`tmp/weighted_CE_seed42`와 `tmp/weighted_RDrop_seed42`는 `structure=FL`, `num_labels=9`, `max_length=256`이다. 제공 예제의 조건부 가지 계산은 `structure=IH`일 때만 실행된다. **이번 제공 모델은 9개 전체 클래스 softmax**이며, 이전 보고의 “선택 가지 조건부 확률” 설명을 정정한다.

`ensemble_seed42`는 세 번째 가중치가 아니라 두 모델의 50:50 확률 평균 설정이다. 앙상블에 다시 softmax를 적용하지 않는다. 둘의 검증 Macro-F1은 각각 약 0.72397·0.72422이고 앙상블 평가 지표는 미제공이므로, 앙상블의 성능 우위를 단정하지 않는다.

현재 앱의 `AutoModelForSequenceClassification` + `model.safetensors` 로더는 제공된 encoder 설정 + custom linear head + `model.pt` 포맷을 직접 지원하지 않는다. 기존 API 인터페이스에 맞는 어댑터를 구현한다. 모델 명세와 인수·실행 조건은 [개정 모델 인수 계획](MODEL_INTAKE_2026-11-17.md)을 따른다.

### 5.2 API·길이·저장 정책

`POST /api/analyze`의 기록 ID·원문 버전·요청 ID, model_version, 9개 확률, 대표 감정·동률·단계·키·정책 버전 구조를 유지한다. 현재 스키마·Pydantic·프론트 응답 검사·mock·fixture의 10개 키를 함께 변경한다. 입력 오류 422, 모델 미준비 503, 추론·출력 오류 500 및 분석 불가 응답을 구분한다.

10,000자는 기록 보관 한도이고 모델 입력 한도는 256토큰이다. 토크나이저로 전체 길이를 먼저 계산해 256 초과 시 기존 분석 불가 계약을 사용한다. 예제의 무조건 `truncation=True` 동작을 운영에 그대로 복사하지 않는다. 문장별 투표·임의 청크 평균은 이번 기본 정책에 넣지 않는다.

이미 구현된 snapshot v2와 revision·요청 경쟁 방지를 보존한다. 10분류 분석은 9분류 분석으로 재표기하거나 억지로 분할·병합하지 않는다. 원문·초안·날짜·ID·즐겨찾기를 보존하고 구형 분석은 새 결과와 구분해 재분석 가능 상태로 옮긴다. 분류 필터에 남은 `neu_4` 등 무효 선택도 해제한다. DB 구조 변경이 없으면 snapshot 버전 숫자를 임의로 다시 올리지 않는다.

## 6. 목표 디렉터리와 정리 원칙

이미 존재하는 `frontend/src/`, `backend/app/`, `contracts/`, `infra/`를 이어서 사용한다. 모델과 이미지 원본은 `tmp/`에서 읽어 인수 목록으로 관리하고 원본을 보존한다. 실행용 모델 묶음은 `models/emotion-9class/` 같은 명시 경로에 세 형제 디렉터리를 함께 배치하거나 해당 상위 디렉터리를 읽기 전용 마운트한다. 학습자의 절대경로는 운영 참조에서 제거한다.

최종 이미지는 버전/해시가 있는 경로로 `frontend/public/assets/cards/`에 연결하고 27키 manifest로 관리한다. 구형 `src/emotion_service/`, `static/`, `backend/main.py`, 루트 Dockerfile, 단일 HTML 생성·테스트 경로는 새 서비스와 시각 검증 후 보관·참조 갱신한다.

현재 `.dockerignore`에는 `tmp/`가 빠져 있다. 모델·이미지 원본이 불필요하게 빌드 컨텍스트나 Git 변경에 섞이지 않도록 제외 정책을 보완한다. 최종 제공 자산만 별도 복사하고, 기존 보고서·라이선스·사용 중인 공유 도메인 파일은 참조 조사 없이 이동하지 않는다.

## 7. 카드 이미지 인수·렌더링

목표는 9감정×3단계=27키다. 최신 수정 파일명과 내용을 확인한 결과 **9감정 각 3단계, 총 27장의 원본이 모두 확보되었다.** 불안 3장의 제공 대기와 놀람 카드 3장의 라벨 확인 조건은 해소되었다. 파일명의 `놀람`은 모델의 통합 라벨 `놀람·당황(neu_3)`에 대응한다. [카드 이미지 인수·27키 매핑 확인서](CARD_ASSET_INTAKE_2026-11-17.md)에 정확한 파일명·크기·SHA-256 식별값을 기록했다.

폴더의 전체 PNG는 28개이며 발급용 27장 외에는 빈 템플릿 1개뿐이다. 템플릿은 감정 카드 발급 대상에서 제외하고 원본으로 보존한다. 27개 카드 키 누락·중복과 동일 SHA-256은 없다. 현재 앱 manifest는 여전히 30개 placeholder이므로 **자산 확보는 완료, 앱 연결·렌더링·PNG 검증은 미완료**로 구분한다.

제공 샘플을 열어 카드 프레임을 포함한 완성 이미지임을 확인했다. 크기는 주로 약 3:4 또는 5:7로 기존 프레임 2:3과 다르다. 현재 `cardRenderer.js`는 이를 캐릭터 영역 안에 넣으므로 manifest 교체만으로 완성되지 않는다. 기존 화면 카드 프레임 안에 비율을 보존해 전체 아트를 배치하고, 메타데이터·PNG 출력에 같은 렌더 경로를 적용한다. 자르거나 늘리지 않고 프레임 이중 표시·글자 겹침을 검수한다.

IMAGE-01은 확보한 27장을 배포 자산으로 연결하고, 9분류 manifest·full_card 렌더링·화면/PNG 일치 검증을 마친 뒤 완료로 처리한다. 자산 제공 대기 없이 연결 작업을 진행할 수 있다.

## 8. 단계별 업무 배분

[후속 작업 계획 4절](REMAINING_WORK_PLAN_2026-11-17.md#4-완성까지의-작업-순서와-담당)을 실행 목록으로 사용한다. 담당자는 실제 인명이 없어 역할로 배정한다.

1. `N9-CONTRACT`: BE·FE가 9분류 계약과 fixture 확정.
2. `N9-FE` / `N9-MODEL`: FE의 공통 도메인 전환과 ML·BE의 실제 모델 연결을 병행.
3. `N9-DATA` / `N9-IMAGE`: FE가 구형 분석 이전·복원과 제공 아트 연결 완성.
4. `N9-OPS`: 인프라가 실제 모델 묶음·Compose·장애·부하 검증.
5. `N9-VISUAL` / `N9-QA`: QA·디자인이 시각·데이터·실제 모델 전체 흐름 검증.
6. `N9-CLEAN` / `N9-RELEASE`: 조정·인프라가 정리·문서·복구·배포 후보 확정.

기존 단계 ID와의 대응, 병행 의존 관계, 파일별 수정 범위와 완료 기준은 후속 표에 명시한다. 다른 에이전트의 작업을 덮어쓰기 전에 대상 파일의 최신 변경 상태를 다시 확인한다.

## 9. Nginx·Compose 보완

기존 두 서비스, prefix 유지 프록시, 정적 파일 404, liveness/readiness, API 재시작 후 DNS 재해석을 재사용한다. 모델 묶음 전체를 읽기 전용 마운트하고 mock 기본값 0을 유지한다. `.env.example`의 6감정 체크포인트 기본 경로를 갱신하고 로컬 `.env`는 자동 덮어쓰지 않는다.

기존 ops 결과에는 `create_host_path:false`에도 Docker Desktop이 빈 디렉터리를 만든 사례가 있다. 따라서 설정만으로 “없으면 반드시 시작 차단”을 보장하지 않는다. 호스트 경로 사전 검사와 준비 상태 실패를 검증한다. 앙상블 메모리·CPU/GPU·cold start·지연을 측정해 worker 1·healthcheck 유예·Nginx 및 클라이언트 timeout을 조정한다.
